## 1. 一笔说不清的账

假设用户在 AI 伴侣里充值了 10 美元，连续聊了几轮，余额变成了 9.96 美元。相比“本次消耗了多少 Token”，用户更关心的是：这 0.04 美元究竟是怎样算出来的？

如果后台只能查到“模型返回了 12,000 个 Token”，我们依然解释不了这笔账。12,000 个 Token 里面可能包含输入、输出、缓存读取和推理用量，每一部分的单价都可能不同。中转站还会叠加渠道倍率、用户折扣或高峰价格。余额只是最终结果，核账时需要的是这次计算采用的用量、价格和规则。

本文所说的 Token 是模型计量单位，不是登录系统里的 `access token`。前者用于衡量模型用量，后者用于证明用户身份。两者名称相同，含义却没有关系。

## 2. Token 的含义

我们在输入框里看到的是文字，模型接收的却是一串整数。文本进入模型以前，要先经过 **tokenizer**。Tokenizer 根据当前模型的词表和切分规则，把原始文本拆成 Token，并将每个 Token 转换成对应的编号。

它的处理过程如下：

tokenizer-flow.txt

```txt
原始文本
  -> tokenizer 切分
  -> Token ID 序列
  -> 模型计算下一个 Token 的概率
  -> 逐个生成新的 Token
  -> tokenizer 解码为文字
```

Token 既不是汉字，也不等同于英文单词，可以把它理解为词表中的一段字符片段。常见英文单词可能只占一个 Token，较长或少见的单词则会被拆成几段；空格、标点、换行和代码符号也会参与切分。中文有时按单个汉字切分，有时会把常见词组放进同一个 Token，遇到生僻字时，一个汉字也可能需要多个 Token 表示。

模型每一步预测的都是下一个 Token ID，所以流式响应准确地说是**逐 Token 输出**。经过 tokenizer 解码后，一个 Token 可能显示成一个汉字、一段英文、一个标点，也可能只是英文单词前面的空格。

同一段文本换一套 tokenizer，得到的 Token 数量可能就会变化。因此，Token 统计必须和模型绑定，旧模型的结果不能直接拿来给新模型计费。我们可以在 [OpenAI Tokenizer](https://platform.openai.com/tokenizer/) 中观察文本的切分方式；生成正式账单时，仍以上游响应中的 `usage` 为准。

## 3. 字符数与 Token

在讨论 Token 以前，还要先弄清楚“字符数”指的是什么。以 JavaScript 为例，`string.length` 统计的是 UTF-16 code unit，并不等于用户肉眼看到的字符数。展开字符串得到的是 Unicode code point；由多人、肤色或连接符组成的 Emoji 可能包含多个 code point，界面上却只显示为一个字形。

| 文本 | string.length | Unicode code point | 用户看到的字形 | Token 数量 |
| --- | --- | --- | --- | --- |
| hello world | 11 | 11 | 11 | 必须交给对应模型的 tokenizer |
| 你好，世界 | 5 | 5 | 5 | 不能由汉字数直接推出 |
| 👨‍👩‍👧‍👦 | 11 | 7 | 1 | 通常会占用多个 Token |
| const total = price * count | 27 | 27 | 27 | 会受到关键字、空格和符号影响 |

浏览器提供的 `Intl.Segmenter` 可以帮助我们观察前三种长度的差异：

inspect-text-length.ts

```typescript
export function inspectTextLength(text: string) {
  const segmenter = new Intl.Segmenter('zh-CN', {
    granularity: 'grapheme',
  })

  return {
    utf16Units: text.length,
    codePoints: [...text].length,
    graphemes: [...segmenter.segment(text)].length,
  }
}
```

返回值中没有 `tokens` 字段，因为浏览器不知道请求会交给哪个模型，也没有对应的模型词表。Token 数量只能交给目标模型的 tokenizer 计算。

OpenAI 为常见英文文本提供过一个估算值：**1 个 Token 大约对应 4 个英文字符，或者四分之三个英文单词**。这个比例只能用来估算容量，不能直接套在中文上，更不能拿来生成正式账单。中文、英文混排、Emoji、Markdown、代码和 JSON 的 Token 密度差异很大。即使字符数相同，连续自然语言、压缩后的 JSON 和带大量缩进的代码也会得到不同结果。

用户输入框里的文字还不是完整的模型输入。一次 Agent 请求通常会拼接系统提示词、历史消息、长期记忆、RAG 检索结果、工具定义以及前几轮工具返回值。用户只输入了 20 个汉字，上游却统计出几千个输入 Token，并不一定是计量错误，大部分上下文可能来自系统自动补充的内容。

## 4. GPT-5.6 Sol 计费示例

接下来用 `gpt-5.6-sol` 算一笔费用。`gpt-5.6` 是模型别名，当前会路由到 `gpt-5.6-sol`。根据撰写本文时的 [GPT-5.6 Sol 官方模型页面](https://developers.openai.com/api/docs/models/gpt-5.6-sol)，文本价格按每 100 万 Token 计算：

| 计费项 | 每 100 万 Token | 说明 |
| --- | --- | --- |
| 普通输入 | 5 美元 | 系统提示词、消息、工具定义等未命中缓存的输入 |
| 缓存读取 | 0.5 美元 | 从 Prompt Cache 复用的输入 Token |
| 输出 | 30 美元 | 可见回答、工具调用参数和推理 Token 等输出用量 |
| 缓存写入 | 6.25 美元 | 官方按普通输入价格的 1.25 倍计费，此处为折算结果 |

模型价格会调整，生产系统不能把表里的数字写死在业务代码中。后面实现模型定价中心时，我们会保存价格版本，让每一笔请求引用开始调用时生效的价格。

假设 Responses API 返回了下面这份用量。为了看清字段之间的包含关系，示例只保留文本计费需要的部分：

gpt-5.6-sol-usage.json

```json
{
  "usage": {
    "input_tokens": 2400,
    "input_tokens_details": {
      "cached_tokens": 1600
    },
    "output_tokens": 500,
    "output_tokens_details": {
      "reasoning_tokens": 220
    },
    "total_tokens": 2900
  }
}
```

先看输入部分。`cached_tokens` 是 `input_tokens` 的子集，普通输入应当是 `2,400 - 1,600 = 800`，而不是 2,400。输出部分也是同样的关系：`reasoning_tokens` 是 `output_tokens` 的明细，不能在 500 个输出 Token 之外再加 220 个。后续为了统一不同厂商的字段，我们会把输出拆成 280 个普通输出和 220 个推理 Token；按照 GPT-5.6 Sol 当前的价格，两部分都使用输出单价，合计仍是 500 个输出 Token。

  &= \frac{800}{1{,}000{,}000} \times 5

  = 0.0008\ \text{美元} \\

  &= \frac{500}{1{,}000{,}000} \times 30

GPT-5.6 Sol 还设置了长上下文价格：输入超过 272K Token 后，整个请求的输入价格按 2 倍计算，输出价格按 1.5 倍计算。加价范围是符合条件的整次请求，并非只计算超出 272K 的部分。因此，计费引擎要先判断输入规模，再选择对应价格。

## 5. Token 用量分类

前面的例子已经出现了普通输入、缓存读取、普通输出和推理 Token。换成其他模型或多模态能力，一次调用还可能返回更多计量项：

| 用量 | 含义 | 常见价格特点 |
| --- | --- | --- |
| 普通输入 | Prompt、历史消息、RAG 内容和工具定义 | 通常低于输出价格 |
| 普通输出 | 模型生成的文字或工具调用参数 | 通常价格较高 |
| 缓存创建 | 首次写入 Prompt Cache 的内容 | 可能高于普通输入 |
| 缓存读取 | 后续请求复用的缓存内容 | 通常明显低于普通输入 |
| 推理 Token | 推理模型内部计算所消耗的 Token | 可能是输出总量的子集，也可能使用独立字段 |
| 图片或音频 Token | 多模态内容被模型编码后的用量 | 可能使用独立价格 |

内部计费结构需要保证各个桶互不重叠。上游的 `input_tokens` 如果已经包含 `cached_tokens`，就要先扣除缓存读取量，再得到普通输入；`output_tokens` 如果包含 `reasoning_tokens`，也要先拆分再写入内部结构。忽略这种包含关系，同一批 Token 就会被重复收费。

Token 也不是 AI 平台唯一的收费单位。网页搜索、代码执行和部分托管工具可能按调用次数收费，图片、音频和视频还可能按尺寸或时长计价。计费引擎需要按照能力类型选择公式，不能看到 Token 为零就判定这次调用免费。

## 6. 用量、成本与售价

一笔模型调用会同时产生三个性质不同的数字：**用量**记录模型处理了多少内容，**上游成本**记录平台为调用付出了多少钱，**用户售价**则决定从用户余额或套餐额度中扣除多少。

它们的关系如下图所示。同一份 Usage 会进入两条计算分支：上游成本使用实际账号对应的成本价，用户售价使用平台为当前用户配置的销售价格和倍率。

用量本身没有货币单位。假设一次调用包含普通输入、缓存读取和输出三个互斥的计量桶，可以记成：

U=(U输入,U缓存,U输出)U = \left(U_{\text{输入}}, U_{\text{缓存}}, U_{\text{输出}}\right)U=(U输入​,U缓存​,U输出​)

上游成本价和用户销售价都按每 100 万 Token 保存。对于任意计量桶 bbb，分别用 PbcostP_b^{\text{cost}}Pbcost​ 和 PbsaleP_b^{\text{sale}}Pbsale​ 表示两套价格。上游成本与用户售价可以写成下面的公式：

  &= \sum_{b \in B} \frac{U_b}{1{,}000{,}000} P_b^{\text{cost}} \\
C_{\text{user}}
  &= \operatorname{round}\left(
    \sum_{b \in B} \frac{U_b}{1{,}000{,}000} P_b^{\text{sale}}
    \times R_{\text{user}}

再用一组具体数字算一遍。普通输入为 2,000 Token，缓存读取为 800 Token，输出为 300 Token；对应的上游价格分别是每百万 Token 2 美元、0.2 美元和 10 美元。为了便于观察计算过程，示例让用户销售价与上游成本价相同，再应用 1.2 倍用户倍率：

最终账单不能只留下 `0.008592`。三种 Token 数量、上游成本价格快照、用户销售价格快照、倍率、价格版本和舍入结果都要一并保存。用户提出疑问时，可以据此复算扣费；平台统计毛利时，也能准确区分成本和收入。

## 7. 用字符数预估 Token

正式账单不能按字符数生成，不过在调用开始前，字符数可以帮助我们估算预算。此时中转站还拿不到最终 `usage`，但它需要提前判断余额是否足够，因此要先估算输入规模和最大输出成本。

估算时不要规定“一个汉字等于一个 Token”，而应当按模型和内容类型建立样本。我们可以收集脱敏后的中文对话、英文对话、代码、JSON 和 RAG 文档片段，使用目标模型对应的 tokenizer 统计 Token 数，再计算每类样本的 Token 密度：

token-density.txt

```txt
样本 Token 密度 = 样本 Token 数 / 样本 Unicode 字符数

预估输入 Token =
  业务文本字符数 * 对应内容类型的 P95 Token 密度
  + 系统提示词 Token
  + 历史消息 Token
  + 工具定义 Token
  + 协议开销与安全余量
```

建议使用 P95 而不是平均值，让估算能够覆盖生僻字、代码和 Emoji 较多的请求。预估值只用于准入、预占和界面提示，模型完成后仍要使用真实 `usage` 结算。如果上游没有返回 usage，估算结果必须标记为 `estimated`，并进入待对账流程。

产品界面可以继续用“还可输入 2,000 字”这种容易理解的方式提示用户，模型网关和财务系统则要把它换算成带有模型版本和误差范围的 Token 预算。字符额度和 Token 额度可以同时存在，只是不能共用同一个数值口径。

## 8. 请求计费流程

余额检查不能拖到模型回答结束以后。一段长时间运行的流式回答可能已经在上游产生费用，如果这时才发现用户只剩 0.0001 美元，差额就只能由平台承担。

一笔完整的请求会经过四个计费阶段：

- **准入检查**：验证 API Key、用户状态、余额、套餐、配额和并发限制。

- **费用预占**：根据模型、输入规模和最大输出估算上限，临时冻结一部分余额。

- **实际计量**：从上游响应中提取真实 usage，并归一化成内部结构。

- **结算入账**：按请求开始时冻结的价格计算实际费用，写入账本，释放剩余预占。

预占不是最终扣费，它更像支付系统中的授权：调用开始前先确认用户有支付能力，完成后再按真实金额结算。请求失败、取消或超时时，则根据是否已经产生上游用量，决定结算已经发生的费用还是释放预占金额。

## 9. 统一用量结构

OpenAI、Anthropic 和 Gemini 的原始用量字段并不一致。如果让业务层分别判断厂商字段，计算逻辑很快就会散落到各个模块。为此，我们先定义一个内部计量对象：

normalized-usage.ts

```typescript
export interface NormalizedUsage {
  regularInputTokens: number
  outputTokens: number
  cacheWriteTokens: number
  cacheReadTokens: number
  reasoningTokens: number
  imageInputTokens: number
  imageOutputTokens: number
  source: 'provider' | 'estimated'
}
```

`source` 用来区分用量证据。`provider` 表示上游明确返回了用量，可以进入正式账单；`estimated` 表示系统因异常而使用 tokenizer 估算。生产环境需要为估算账单设置单独策略，例如暂缓扣费或放入待对账队列，不能把估算结果当成精确数字。

模型请求、Embedding、图片生成和网页搜索也不一定都按 Token 计费。统一结构负责告诉计费引擎当前拿到了哪些证据，再由引擎选择 `token`、`per_request`、`image` 或其他计费模式，无需强行让所有能力共用一套公式。

## 10. 计费系统的约束

算出费用只是计费系统的第一步。系统还要保证：相同请求重试不会重复扣费；并发请求不能同时花掉同一份余额；价格更新不会改变历史账单；缓存故障不会让所有用户免费调用；管理员调整余额必须留下原因和操作记录。

后续文章会继续使用这个案例，逐步实现这些约束。AI 伴侣的模型请求会先经过 Hono 中转站，由中转站负责鉴权、调度、计量和结算。LangChain 与 LangGraph 可以记录一次 Agent 运行经过了哪些节点，适合做费用归因，但不能代替网关从上游取得的 usage。

## 11. 总结

Token 是 tokenizer 按模型词表切分出来的字符片段，与汉字数、单词数或 JavaScript 的字符串长度都没有固定换算关系。字符数可以帮助产品限制输入，也能基于真实样本估算调用上限，但正式费用仍要使用目标模型返回的 usage。

一笔完整的 Token 账单应当串起用量、价格、倍率和余额变化：上游返回了多少普通输入、缓存、输出和推理用量，当时使用哪份价格，经过什么倍率，最后扣除了多少余额。只保留总 Token 或最终金额，都无法支持对账和审计。

下一篇会进入中转站的整体架构，梳理请求准入、上游转发和账务结算各自负责什么。职责边界确定以后，再设计数据表和服务接口会清楚很多。
