## 1. 执行计划

上一篇结束时，Agent 已经知道用户明天要坐高铁去上海出差，行程持续三天，需要参加产品评审，第二天还要拜访客户。只有天气仍需通过外部工具查询，用户侧的关键信息已经补齐。

现在直接让模型生成物品清单，看起来也能得到答案。但这会把「查天气」「分析工作场景」「整理清单」「检查遗漏」全部藏进一次模型调用里。结果一旦不合适，我们很难知道是天气没有查、客户拜访场景被忽略，还是最终检查没有发生。

执行计划的作用，就是在真正行动之前，把这段隐藏的思考变成可以观察的步骤。它不负责完成任务，而是先回答四个问题：要做哪些事、谁来做、先后关系是什么、做到什么程度才算结束。

因此，这一篇不会重新识别意图，也不会重新抽取和补全信息。它直接接收上一篇保存的结构化状态，只执行新的第四步：制定执行计划。

## 2. 执行说明

用户最终要的是一份物品清单，计划却可能长成这样：先查询上海天气，再整理三天行程和两个工作场景，然后根据前两步的结果生成分组清单，最后检查清单是否满足目标。

这段内容还不能直接交付给用户，因为「查询天气」尚未真的发生，「生成清单」也只是一个待执行动作。它更像 Agent 写给自己的执行说明。

| 内容 | 回答的问题 | 当前案例 |
| --- | --- | --- |
| goal | 最终要得到什么 | 得到适合这次上海出差的物品清单 |
| 执行计划 | 为了目标要依次做什么 | 查天气、整理需求、生成清单、检查结果 |
| 最终答案 | 用户实际拿到什么 | 根据真实天气和行程生成的物品清单 |

这里最容易混淆的是 `goal` 和计划。`goal` 是终点，计划是到达终点的路线。路线中的某一步失败时，Agent 可以重试或换路；只要 `goal` 没变，就不必重新猜测用户到底想做什么。

## 3. 字段说明

只让模型返回「第一步查天气，第二步列清单」，人可以大致看懂，程序却很难可靠执行。为了让后续代码能够调度这些步骤，案例为计划增加了几个字段。

| 字段 | 最直白的含义 | 它给 Agent 增加的复杂度 |
| --- | --- | --- |
| id | 这一步叫什么 | 系统要保证唯一，并用它记录状态和日志 |
| title | 这一步做什么 | 动作必须足够明确，不能只写「处理一下」 |
| type | 由谁来做 | 系统会分流到工具、模型推理或验证逻辑 |
| dependsOn | 必须等谁完成 | 系统要处理等待、并行、无效引用和循环依赖 |
| expectedOutput | 这一步应产出什么 | 后一步才能判断拿到的数据是否可用 |
| completionCriteria | 整体何时结束 | 系统必须检查目标，而不是步骤跑完就宣布成功 |

其中 `dependsOn` 对复杂度的影响最大。没有依赖时，步骤只是一个从上到下的列表；加入依赖后，它会变成一张图。图中的两个步骤可能并行运行，也可能等待同一个前置结果，还可能因为配置错误互相等待。

图里「查询上海天气」与「整理行程需求」互不依赖，所以可以并行。生成分组清单需要同时使用天气和行程结果，必须等两步都完成。最后的验证步骤再用 `goal` 检查计划产物，而不是仅仅检查前面的函数有没有返回。

从这里开始，Agent 不再只是「问一次模型，拿一个答案」。它还要保存步骤状态、选择执行器、等待依赖、传递结果并判断终止。字段看起来只多了几个，系统却由一次生成变成了一个小型工作流。

## 4. 案例

下面的演示继续使用前两篇的案例。为了让这一篇能够单独刷新和运行，`context.ts` 保存了上一篇完成澄清后的状态快照。它不是重新伪造一次识别过程，而是在模拟真实 Agent 中由会话状态、数据库或工作流节点传来的输入。

点击「生成上海出差计划」后，你会先看到这份上游状态，包括 `intent`、`goal`、已补全的行程信息和需要工具查询的天气。随后只会出现「第四步：制定执行计划」，前三步不会再次调用模型。

```typescript
export const TRAVEL_CONTEXT = {

  intent: {
    intent: '准备出差所需物品',
    goal: '得到一份适合乘坐高铁去上海出差的物品清单',
    confidence: '高',
  },
  information: {
    time: '明天',
    destination: '上海',
    purpose: '出差',
    duration: '三天',
    explicitDetails: [
      '乘坐高铁',
      '参加产品评审',

    ],
    missingInformation: ['上海明天天气'],
  },
  toolInformation: ['上海明天天气'],

} as const satisfies TravelPlanningContext

```

`context.ts` 的存在很重要。它把「上一篇到底留下了什么」变成可以查看的代码，也让第四步的输入边界变得清楚。在完整项目里，这份对象应由上一篇的流程状态传入；在相互独立的教学页面里使用固定快照，可以避免刷新页面后状态丢失，同时保留学习所需的全部上下文。

`agent.ts` 的主流程只做三件事：读取稳定状态、调用计划模型、规范依赖关系。它不会调用天气工具，也不会生成最终清单。这样我们观察到的结果确实是一份计划，而不是模型把计划和执行混在一起后的回答。

如果你在生成计划后继续输入「我只带一个双肩包，请压缩计划」，演示会沿用当前计划，把新要求作为第四步的补充约束。意图识别、信息抽取和信息补全仍然不会重新执行。

## 5. 总结

制定执行计划，是把「已经理解的目标」转换成「可以被程序调度的步骤」。它承接 `intent`、`goal`、已知信息和工具查询项，但不重复前面的识别与补全过程。

一份可靠计划不仅要写做什么，还要说明步骤类型、依赖关系、预期输出和完成标准。正是这些字段，让 Agent 有能力并行、等待、验证和修改计划，也同时带来了状态管理与错误处理的复杂度。

到这里，我们只完成了规划。下一篇就开始正式执行
