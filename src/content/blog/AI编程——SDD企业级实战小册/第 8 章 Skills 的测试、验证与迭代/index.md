#

> 第二部分：Skills 深度解析

上一章把 Skill 的串联和并联都讲清楚了。组合越复杂，有一个问题就越不能绕开：你怎么知道这套 Skill 跑得对？

代码写完了可以跑单测，逻辑错了测试直接报红。Skill 不一样——写完一个 Skill，没有测试框架帮你断言输出，Claude 每次跑出来的结果也不完全一样。同样的输入，今天输出格式是这样，明天可能换个结构；同样的 Skill，在这个项目触发正常，换个上下文就跑偏了。

这不是 AI 不稳定的锅。是你还没建立起一套针对 Skill 的验证方法。

---

## 8.1　Skill 测试为什么和代码测试不一样

给你两段话：

> “这个函数输入 [1, 2, 3]，必须输出 6。”

> “这个 Skill 输入需求描述，输出一份设计文档。”

第一个可以写断言。第二个没法写断言——“一份设计文档"可以有无数种形式，你期望的不是某个固定字符串，而是"质量达标”。

Skill 测试的目标不是验证输出相等，而是验证三件事：

1. **触发准确**：该触发时触发，不该触发时不触发

2. **输出稳定**：结构和格式在多次运行后保持一致

3. **意图对齐**：Claude 做的事符合你写这个 Skill 时的预期

缺哪一条，Skill 都停留在"能跑但不放心用"的状态。

---

## 8.2　三层测试模型

### 第一层：意图对齐测试

测试问题：Claude 理解这个 Skill 的用途是否正确？

方法极其简单，直接问 Claude：

```
你：你对 /daily-summary 这个 Skill 的理解是什么？
什么时候应该用它？什么时候不应该用它？
```

如果 Claude 的描述和你写 Skill 时的意图不符，说明你的 description 或执行逻辑写得有问题。这一层最容易修——改 description，重新问，五分钟搞定。

Fly哥遇到过一个真实案例：写了一个 /spec-review Skill，本意是审查现有规格文档的完整性，结果 Claude 理解成了"帮我写一份新规格"。问了一下，发现是 description 里写了"生成规格报告"，“生成"两个字有歧义。改成"检查并报告规格文档的问题”，意图立刻对齐了。

意图测试要在每次修改 Skill 后做一遍。Skill 内容一变，Claude 的理解就可能跟着变。

### 第二层：输出稳定性测试

测试问题：相同的输入，每次输出结构是否一致？

方法：在真实场景下触发 3–5 次，对比输出。

检查点：

- 输出的章节结构每次一致吗？

- 有没有某个字段这次有、下次没有？

- 列表项数量稳定吗，还是时多时少？

- 有没有幻觉——输出了当前上下文里不存在的信息？

不稳定的常见原因有三个：

**执行步骤描述太模糊。** “分析代码"这四个字 Claude 每次解读方式都不一样。改成"列出所有导出函数的名称和参数”，就稳多了。越具体，越稳定——这是针对 AI 的"类型约束"。

**输出格式没有明确定义。** “生成一份报告”——长什么样？几个部分？每部分叫什么？不写清楚，每次输出结构都会漂移。Skill 里加一个"输出格式"部分，给一个具体的 Markdown 模板，稳定性立刻提升。

**Skill 做了太多事。** 一个 Skill 里塞了 8 个步骤，Claude 偶尔会跳过其中某些步骤。把步骤改成 checklist 格式——- [ ] 步骤一——强制逐步执行，漏步率会显著下降。

### 第三层：边界行为测试

测试问题：在非典型输入下，Skill 会怎么处理？

这层是最容易被忽略的，也是问题最容易藏的地方。

典型边界场景：

场景

测试方式

常见问题

空输入

/daily-summary（今天零提交）

Claude 可能开始编造提交记录

超大输入

100 个文件变更时跑 /requesting-code-review

输出格式可能开始变形

歧义输入

模块名有多种拼写方式时

Claude 可能在多种理解中随机选一个

重复触发

同一 Skill 连续跑两次

第二次可能参考第一次输出，产生意外关联

发现边界问题后，处理方式不是绕过，而是在 Skill 里明确写出边界处理逻辑：

```
## 边界处理
- 如果今日没有任何提交记录，输出"今日暂无提交"并结束，不要尝试推测或生成虚假记录
- 如果变更文件超过 50 个，优先审查被标记为"核心模块"的文件，其余只做摘要
- 如果输入有歧义，列出你理解到的多种可能含义，等待用户确认后再继续
```

写进去了，Skill 遇到极端输入的行为就从"随机应变"变成了"按规则处理"。

## 8.3　从"能跑"到"稳定好用"：迭代四步法

好的 Skill 不是一次写成的，是跑出来的。

一个典型的 Skill 迭代过程大概是这样：

**第一版：能跑**

写一个最小 Skill，把基本流程跑通。这个版本通常输出格式不稳定，偶尔跑偏，边界情况处理全靠碰运气。没关系——第一版的目标就是跑通，不是完美。

**第二版：输出稳定**

跑了几次，把不稳定的地方都找出来：

- 输出格式不一致 → 加"输出格式"部分，给具体模板

- 某步骤经常被跳过 → 改成 checklist 格式，强制逐步执行

- 经常做了不该做的事 → 加"不做什么"的约束列表

这一版之后，运行 5 次应该能得到 4 次结构一致的输出。

**第三版：边界处理完整**

有了稳定输出，再去触碰边界场景。把测出来的边界问题一个个加进 Skill 的边界处理逻辑里。这一版之后，Skill 在非典型输入下也不会乱来。

**第四版：精简**

迭代过程中往往会加入太多约束，Skill 变得臃肿。稳定之后做一次精简：删掉不必要的说明，合并重复的意思，保留真正有效的约束。

精简后的 Skill 往往跑得比第三版更好——越精简，给 Claude 的"解释空间"越小，行为越可预测。

一个铁律：**每次只改一个地方，改完就测。** 同时改多处，出了问题不知道是哪里出的。这条规则在写代码时适用，在迭代 Skill 时一样适用。

## 8.4　版本管理与团队共享

Skill 文件在 .claude/skills/ 目录下，用 git 管理——这本来就是文本文件，没有理由不纳入版本控制。

好的 Skill commit message：

```
fix(daily-summary): add empty-commits guard to prevent hallucination
feat(code-review): add security dimension checklist
refactor(brainstorming): simplify output format, remove redundant steps
```

commit message 说明改了什么、为什么改。三个月后翻 git log，能看到每个版本的 Skill 在解决什么问题，而不是一堆没意义的"update skill"。

团队共享时有几点需要约定：

**修改共享 Skill 前，先在本地测试稳定。** 改了一个 Skill 直接 push，然后发现其他人触发时全跑偏——这种事发生一次就够了，建议写进团队规范。

**改了 Skill 要同步团队，说明行为变了什么。** Skill 改完行为变了，但没人知道——团队其他人按照旧行为在用，结果产出开始不稳定，排查半天才发现是 Skill 被悄悄改了。一条简短的团队消息，能省掉很多来回。

**个人专属的 Skill 本地留着，别提交到团队仓库。** 有些 Skill 是你个人工作流的一部分，别人不需要——加到 .gitignore 就好，别污染共享目录。

如果 Skill 迭代频繁，可以在 frontmatter 里加 changelog 字段做轻量记录：

```
---
name: daily-summary
description: 汇总当日 git 提交，生成工作日报
changelog:
- v1.2 (2026-03-15): 加入空提交守卫，避免生成虚假记录
- v1.1 (2026-03-01): 统一输出格式，加入 checklist 步骤
- v1.0 (2026-02-20): 初始版本
---
```

这不是必须的，但在 Skill 改动频繁时很有用——翻 changelog 比翻 git log 快得多。

## 小结

Skill 的测试不是一次性的，是持续的。每次修改 Skill，意图对齐测试要重新过一遍；隔一段时间，输出稳定性值得重新确认；发布给团队前，边界行为要专门测一轮。

听起来有点麻烦。但比起"Skill 跑偏了才发现、花两倍时间排查"，这个投入完全值得。

Skill 写好了，测稳了。下一个问题是：这些流程，你能保证每次都记得在正确的时机触发吗？
