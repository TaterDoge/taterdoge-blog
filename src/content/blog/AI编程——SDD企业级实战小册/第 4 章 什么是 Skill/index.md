## 4.1　Skill 解决什么问题

上一章我们走马观花过了 SuperPowers、OpenSpec、MCP 三件套，Skill 在那里是作为 SuperPowers 的"构成单元"出现的——但一句话带过，没展开。这一整章，咱们就专门把 Skill 拆清楚。

先从你熟悉的场景说起。

打开 Claude Code、Cursor，或者任何一款 AI 编程工具，新对话开始，第一件事不是写代码，而是手动输入一大段背景交代：“用中文回复”、“修改前先读文件”、“写代码要先写测试”……你把这些规则攒成一段 prompt，存在某个 Notion 页面里，每次开新对话就粘贴一次。

时间一长，你会有一种奇怪的感觉：**你在训练 AI，但每次都要从头来**。

这不是你一个人的问题。很多团队用 AI 辅助开发，效率瓶颈不在"AI 够不够聪明"，而在"你每次都要重新告诉它一遍上下文"。AI 的记忆是一次性的，对话结束，经验清零。你攒的那些"最佳实践"，AI 根本记不住。

Skill 就是为了解决这个问题而存在的。

把那些"每次都要说的话"写成一个 Skill 文件，放进项目里。下次触发的时候，AI 自动读取，按你定义好的逻辑执行，不需要你再开口。**写一次，永久复用。**

更重要的是，Skill 不只是"一句话规则"，它可以是一套完整的工作流：进入什么阶段、按什么顺序执行、遇到边界情况怎么处理、输出什么格式。你把流程沉淀进去，团队里每个人用 /skill-name 触发，得到的是一致的、可预期的结果——不是"今天 AI 心情好，输出还不错"，而是"这个流程我们跑过一百次，稳定"。

这就是 Skill 的核心价值：**把经验结构化，让它可以被复用、被共享、被迭代。**

---

## 4.2　一个 Skill 文件长什么样

Skill 是放在 .(claude | cursor)/skills/ 目录下的 Markdown 文件。就是普通的文本文件，没有魔法，没有编译步骤。

它包含三件事：**是谁**（名字和描述）、**何时启动**（触发条件）、**怎么执行**（具体逻辑）。

最简单的形式长这样：

```
---
name: daily-summary
description: 汇总当日 git 提交，生成每日工作报告
trigger: 用户输入 /daily-summary 时触发
---
# Daily Summary
1. 运行 `git log --since="00:00" --oneline` 获取今日提交
2. 按功能模块分组整理
3. 用中文输出一份 200 字以内的工作摘要
```

就这些。没有 SDK，不用装包，不用写代码。AI 读到这个文件，下次看到 /daily-summary，就知道该做什么了。

## 你现在可能觉得"这也太简单了"。对，故意的。Skill 的门槛很低，低到任何人都能写。

## 4.3　Skill 和 Slash Command 是什么关系

很多人第一次见到 /brainstorming、/writing-plans、/code-review 这些命令，以为是 Claude Code 的内置功能，官方预装的那种。

不是。这些全是 Skill 文件。

准确说法是：**Command 是入口，Skill 是引擎。**

你输入 /brainstorming，我这里以Claude Code 去举例子， Claude Code 去 .claude/skills/ 目录找名为 brainstorming.md 的文件，找到了就加载进上下文，按里面定义的逻辑执行。文件不存在，什么都不发生。就这么简单。 Cursor 呢就会去找 .cursor下的 skills/，依此类推。

这个设计有个非常重要的推论：

- **你自己创建 Skill，就有了自己的 Slash Command**——不需要等官方更新，不需要申请权限

- **修改现有 Skill，就改变了 Command 的行为**——迭代很低成本

- **团队共享同一套 Skill，工作流就统一了**——新人入职，clone 仓库，立刻拥有和老人一样的 AI 工作流

> 每次新写一个SKILL ，记得重新启动 cursor或者claude code

最后一点，Fly哥觉得是被严重低估的价值。以前团队里"谁会用 AI"靠个人摸索，经验留在脑子里，换人就断层。现在经验沉淀进 Skill 文件，交接的时候直接 git clone，AI 的使用方式都跟着走。

## 4.4　Skill 的三个核心结构

### frontmatter：让 AI 知道"这是什么"

```
---
name: skill-name          # 唯一标识，对应 Slash Command 名称
description: 一句话说清楚这个 Skill 做什么，何时用
trigger: 触发条件描述
---
```

description 是这里最关键的字段。

AI 决定要不要激活某个 Skill，靠的就是这一句话。写模糊了，后果是两种：要么乱触发（你说了别的事 Skill 也跑出来），要么该动时不动（你明确触发了但 AI 没认出来）。

好的 description 要回答两个问题：这个 Skill **做什么**，以及**什么情况下用**。

差的写法：帮助用户进行代码审查

好的写法：当用户完成一个功能模块并输入 /code-review 时触发。检查代码质量、安全隐患和测试覆盖，输出结构化审查报告。

---

### 触发条件：显式 vs 隐式

触发分两种，行为差异很大：

**显式触发**：用户主动输入对应的 Slash Command（/skill-name）。你控制，你决定。SDD 流程里大多数关键节点都走显式触发——你清楚地知道现在进入了哪个阶段。

**隐式触发**：AI 根据当前对话内容，判断某个 Skill 的 description 和场景匹配，自动加载执行。不需要你记命令，但也意味着你对触发时机的控制力弱一些。

两种方式没有优劣，取决于你要封装的工作流的性质。对于流程明确、阶段清晰的场景，显式触发更可靠；对于"随时都可能需要"的辅助类 Skill（比如自动用中文回复、自动读文件再改），隐式触发更自然。

---

### 执行逻辑：具体到能被机器理解

Skill 的正文就是执行逻辑。格式不限，可以是 checklist、决策树、固定的输出模板，或者调用另一个 Skill。

有一个铁律：**写得越具体，输出越稳定。**

“分析用户需求”——这是没用的。AI 不知道"分析"意味着什么动作，输出会随机漂移。

“列出 3 个实现方案，每个方案写清楚：技术选型、优缺点、推荐指数（1-5 星）和推荐理由”——这是可执行的指令，输出结构固定，可以被比较、被评审、被存档。

执行逻辑写不好，Skill 就是个摆设。这也是为什么后面要专门讲 Skill 的测试和迭代——Skill 不是写完就完了，要跑，要对比，要打磨。

---

## 小结：Skill 是你和 AI 协作的"接口"

普通的 AI 使用方式，是你每次用自然语言"描述清楚需求，希望 AI 理解"。这种方式不稳定——你今天描述的方式和昨天略有不同，AI 给出的结果就不一样。

Skill 把这件事翻转了：**你定义接口，AI 遵守接口。**

你不再每次祈祷 AI 理解你的意图，而是提前把意图结构化成 Skill，让 AI 按规则执行。这不是在限制 AI，是在让 AI 的能力被稳定地释放出来。

下一章，我们来看 Skill 和 MCP 的关系——两个经常被混淆的概念，搞清楚它们的边界，你对整个工具链的理解会清晰很多。
