## 第一站：需求脑暴

我见过最亏的返工，不是写错一行代码，是「两边都写完了才发现名词对不上」。有一次做小游戏功能，前端默认「次数在前端扣」，后端默认「次数落库」，联调那天才发现——改哪边都疼。两套状态机已经写了三天，接口都联通了，但数据源就是对不上。最后前端妥协，把那段本地状态全删了重来。三天没了。

从那以后我信一句话：在代码里做的决定，成本往往是需求阶段的两倍起跳。不是夸张，是账。

/brainstorming 干的事，就是把那些本该提前想清楚的假设，硬拽到动手之前。命令的本体是一个 Skill，挂在项目 .claude/commands/brainstorming.md 下，触发后 AI 进入「先问后答」模式——但在这之前，如果你是独立开发者、脑子里还只有一个模糊想法，有两步得先走完。

## 11.0 独立开发者的第零步：先把想法审一遍

企业项目的起点通常是已经给定的需求——PRD 在那，你负责拆解执行。但如果你是独立开发者，自己想做一个东西，起点是一个念头：「我感觉这个方向有搞头。」

这时候直接跑 /brainstorming 会有个问题：它擅长把模糊需求问清楚，但它不会质疑你的方向本身是否值得做。如果方向本身就跑偏了，后面的技术设计做得再严谨，也是在错的地方走对的路。

所以独立开发者的前置链路是这样的：

```
原始想法
→ deep research（市场/竞品/用户扫描）
→ /office-hours（YC 式六问，逼你重构产品定义）
→ /brainstorming（技术方案拆解）
→ design.md 落地
```

### 第一步：deep research

想法有了，先别开会，先开研究。用 Perplexity、ChatGPT Deep Research 或 Claude 的联网模式，把这几个问题跑一遍：

- 这个领域已经有什么？（竞品清单，不少于 5 个）

- 用户在哪里抱怨现有方案？（Reddit、V2EX、App Store 评论、ProductHunt 留言）

- 有没有已经死掉的类似项目？死因是什么？

不需要报告形式，要点就行。这一步的目的不是「验证我的想法是对的」，而是搞清楚你进入的是什么战场、地雷在哪。Fly哥做过一个工具，研究完才发现某个大厂六个月前上了一个一模一样的免费版——早知道早转向，浪费了两周。

### 第二步：/office-hours

deep research 给了你信息，/office-hours 负责用这些信息逼你想清楚。这是 gstack

[https://github.com/garrytan/gstack](https://github.com/garrytan/gstack)

工具链里的一个 Skill，核心机制是 YC Office Hours 模式——六个强制性问题，挨个逼你正面回答：

Skill

角色定位

做什么

/office-hours

YC Office Hours

六个逼问，重构你的产品定义。推翻你的预设，挑战假设，生成替代方向。产出的 design doc 会喂给后续所有 Skill。

六问不是聊天，是审讯。每一问都在挑你立场：

1. 你到底在做什么，用一句话说，不许说「平台」「生态」「赋能」

2. 谁会第一个用，具体的人，不是「开发者群体」

3. 他们为什么不用现有方案，你的差异点必须是他们现在真正在抱怨的事

4. 这件事最难的环节在哪，你打算怎么过

5. 第一个用户怎么来，不许说「做好了自然会有人来」

6. 为什么是你，为什么是现在，时机窗口在哪，你的不可替代性是什么

这六问跑完，会输出一份小型 design doc：你的产品定义是什么、核心假设是什么、最大风险在哪。这份 doc 不是技术方案，而是方向的共识文件——你确认自己想做这件事、知道在赌什么，然后再把它交给 /brainstorming 做技术拆解。

企业项目里这一步通常已经有人替你做了（PM、老板或者需求文档）。独立开发者没有，得自己走一遍。省掉这步就是在省「发现方向错了」的时间——省掉了，代价是更晚发现。

走完这两步，/brainstorming 接手的就不再是一个模糊念头，而是一个已经被审过的想法：市场摸清楚了，方向确认了，风险也知道在哪。接下来是技术的事。

## 11.1 怎么描述需求，AI 才会问到点子上

命令跑起来以后，AI 往往不先给方案，先丢问题。第一次用的人会不爽：我都说了要做啥，你咋还问？

把顺序反过来就顺了。你写出来的是你「以为已经想清楚」的部分；它问的，是你「没意识到必须想清楚」的缝。缝不补，后面就是 bug 和扯皮。

这个案例里，初始描述就一句：

> 我想做一个游戏落地页框架，支持九宫格、转盘、盲盒

就这么一句话，AI 没有直接出方案，而是开始追问。以下是对话的实际节奏：

**AI：** 理解你的目标了。在给出架构方案之前，我需要确认几个会影响设计的关键决策：

- 三种玩法是否共用同一套奖品池？还是每个玩法独立配置？

- 抽奖次数由前端本地状态管理，还是落到后端数据库？

- BFF 层是否需要鉴权？（比如需要登录才能参与）

- 这是单套皮肤，还是要支持多套主题？

**我：** 奖品池各自独立；次数走后端落库；BFF 鉴权，但只校验 token 有效性，权限管理不在这里；先做单皮肤，但架构上预留多皮肤扩展位。

**AI：** 好，现在可以给架构方案了。核心分叉在……

四个问题，没有废话。每个问题背后都是会在代码里分叉的决策。

为什么偏偏问这四个？触发条件通常是边界模糊。「支持三种玩法」没有说数据是否共享 → 问奖品池；「有 BFF」没有说入口是否管控 → 问鉴权；「游戏次数」没有说谁持久化 → 问落库；「落地页」没有说视觉差异度 → 问皮肤。每一问，背后都是一个会分叉的代码路径。

拿「次数谁管」举例。不问这一句，极容易出现：前端本地状态一套、后端持久化一套，联调时才发现方向拧了——重写前端或废字段，怎么选都是沉没成本。

好的追问，本质是假设显性化。你心里藏的默认越多，后期爆炸面越大；brainstorming 每挖出一个，就少一颗雷。

描述需求的黄金公式：**确定的写死，不确定的留白。**

不必先写 PRD，几句自然语言就够。你负责给已知，AI 负责把未知拎到桌面。描述越具体，问题越收敛；描述越飘，问题越散——但「飘」不是罪，AI 能把模糊处追出来；「确定的事写错」才真的麻烦，那它就帮倒忙了。

## 11.2 方案选型：不是让 AI 替你拍板

澄清之后，AI 会摆几套架构，并把代价摊开。注意：目标不是「选一个正确答案」，而是让你在编码前，把「选 A 不选 C 要付什么账」算明白。

本案例里三套路，先看结构长什么样。

### 方案 A（Monorepo + 插件注册表）

```
game-landing-framework/
├── packages/
│   ├── core/           # 注册表、生命周期、公共 hook
│   ├── plugin-grid/    # 九宫格玩法
│   ├── plugin-wheel/   # 转盘玩法
│   ├── plugin-box/     # 盲盒玩法
│   └── bff/            # BFF 层，统一鉴权
├── apps/
│   └── demo/           # 调试用宿主应用
└── package.json        # workspace 配置
```

### 方案 C（单仓平铺）

```
game-landing/
├── src/
│   ├── grid/           # 九宫格
│   ├── wheel/          # 转盘
│   ├── box/            # 盲盒
│   ├── router/         # 三种玩法的路由混在一起
│   ├── store/          # 全局状态，谁都能改
│   └── bff/
└── package.json
```

光看目录就能感受差距。方案 C 里，「九宫格」和「转盘」共享路由和全局状态，加第四种玩法要动这两个文件——测试面瞬间扩到全局。方案 A 里，新玩法是一个新 package，接口对上注册表就收工，存量代码不需要动。

**方案对比：**

- **方案 A：** Monorepo + 插件注册表。玩法独立包，统一接口注册，BFF 与 Service 分层部署。

- **方案 C：** 单仓平铺，所有代码糊在一个应用里。

我见过太多团队选 C 的理由是「先跑起来」。第一个版本确实快。可这个框架的核心价值是「新玩法像插卡一样加进来」——C 天然反着来：每加一个玩法，要动主应用、路由、配置，维护成本线性涨。快是今天的快，慢是两年后的慢。

A 的 upfront 成本更高：workspace、注册表接口、目录规范。这是一次性学费。之后每加一个玩法的边际成本很低：建新包、实现接口、注册，收工。架构给扩展留门，而不是把门焊死。

还有一个角度值得算进去：换人成本。团队里来个新人，接手「增加第四种玩法」这个任务。方案 C 里，他得读懂整个应用的路由和状态机才敢改；方案 A 里，他只需要看 packages/plugin-grid 的结构，照着抄一个新 package，改接口名，收工。一个是读全局，一个是读一个 package。onboard 文档要覆盖的范围，差了一个数量级。换人不是小概率事件，是所有长期项目的标配风险。

这次选型在脑暴阶段就落定，没有写到一半推翻。后面 15 个 Task 能顺推，底子是这一步打的。

Fly哥觉得：选型若拖到编码中，代价不是「想清楚再改」，而是改完才发现方向错了。brainstorming 最大的价值，不是 AI 给了多聪明的方案，而是你在写第一行代码前，把「为什么不是 C」说明白了。

## 11.3 设计文档放哪、写什么

脑暴结束，通常会落一份 design 文档，例如：

docs/superpowers/specs/2026-03-29-sdd-game-landing-framework-design.md

命名习惯：YYYY-MM-DD-<topic>-design.md。日期在前，是因为同一 topic 可能多轮讨论，时间戳是最便宜的版本号。

文档的结构是固定的，大概长这样：

```
# 游戏落地页框架 设计文档
日期：2026-03-29
## 背景与目标
支持九宫格、转盘、盲盒三种玩法的落地页框架。
核心诉求：新玩法接入成本 < 1 天，不影响存量玩法。
## 方案对比
| 方案 | 描述 | 主要代价 |
|------|------|---------|
| A（Monorepo） | 插件注册表，玩法独立包 | workspace 初始化成本 |
| B（多仓+npm） | 版本当契约 | 发布流程管理税 |
| C（单仓平铺） | 快速上线 | 线性增长的维护成本 |
## 最终决策
选方案 A。
## 否决理由
- 方案 B：内部项目不值得付三个仓库的管理税
- 方案 C：框架核心价值是「插卡式」扩展，C 与此背道而驰
## 遗留问题 / 后续 TODO
- [ ] 多皮肤扩展点在 core 层定义，暂不实现
- [ ] BFF 鉴权策略在 proposal 里细化
```

哪些字段必填？背景/目标、方案对比、最终决策、否决理由——这四个缺一不可。

没有否决理由最要命。半年后接手的人不知道「C 为什么没选」，大概率会重新提一遍 C方案，推一遍，发现一样的问题，再否一遍——付了两遍学费，还没人知道。[design.md](http://design.md) 把「为什么不选 C」钉住，就是不想让后人重蹈。

它和后面的 proposal.md 分工不同：

文档

偏重

谁会在意

更新频率

design.md

讨论过程，含被否定的方案与理由

想搞懂「为什么不选 B」的人

脑暴阶段写一次，原则上不改

proposal.md

最终决策，对外对齐与执行

开发阶段天天对照的人

每轮迭代按需更新

只写结论、不写过程，是文档腐烂的常见根因。半年后不知道为什么这么定，只能重推一遍，推完发现还是一样。[design.md](http://design.md) 把过程钉住，就是不想付第二遍学费。

从企业视角看，这也是换人与审计的保险：接手的人、被拉来救火的 AI，都能从同一套叙事进场，而不是靠 oral history。

## 11.4 脑暴结束，意味着什么

设计文档落地，这一站的使命就结束了。

表面看是「聊了一会儿，生了个 md」。实际发生的事更重：架构方向定了，边界清了，关键分叉拍完了。

怎么判断脑暴是否真的结束了？我习惯用一个简单的验收清单：

- 关键技术分叉都有明确答案（次数谁管、鉴权在哪、数据是否共享）

- A/C 方案对比落纸面，否决理由写明白

- [design.md](http://design.md) 已提交进仓库，不是还在本地草稿

- 团队成员（或 AI）能从文档冷启动，不靠口头说明

四条全过，再开工。少一条，就是在赌后面不会踩坑。大多数时候，赌输了。

后面 15 个 Task 能按计划推进、没有中途推翻架构，就是这一步的利息。
